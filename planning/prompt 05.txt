# پرامپت نهایی — ایجنت خودمختار پلتفرم SIM800 (حالت Build-Only + تحویل ZIP)

> **تغییرات اصلی نسبت به نسخه قبلی:**
> - **هیچ clone و هیچ push به مخزن اصلی GitHub انجام نمی‌شود.**
> - ایجنت پروژه را **از صفر و کاملاً درون workspace خودش** می‌سازد.
> - مرجع پروژه (vision) در همین پرامپت (بخش ۰.۵) گنجانده شده تا نیاز به خواندن مخزن اصلی نباشد.
> - دیتاشیت PDFها همچنان از مخزن جداگانه `Package-Datasheet-sim800` خوانده می‌شوند (فقط read-only).
> - خروجی نهایی: **یک آرشیو قابل دانلود (`.zip` + `.tar.gz`)** شامل کل پروژه با تاریخچه Git محلی، داده، مستندات و گزارش‌ها.
> - تمام منطق‌های «push access»، «credential helper موقت»، «branch روی remote»، «GitHub API permissions» حذف شدند.
> - Git فقط **به‌صورت محلی** استفاده می‌شود: `git init`, `git add`, `git commit`. هیچ remote، هیچ push.

## ⚡ Quick Start (۳۰ ثانیه)

ترتیب اجرا:

1. **تشخیص وضعیت:** اگر `PROJECT_STATE.md` در `/workspace/build/sim800-platform-all/` وجود دارد و Memory Bank آن پر است → **Resume**. در غیر این صورت → **First Run**.
2. **First Run:** Capability Test → Persistence Test → Datasheet Access Verification → **توقف و گزارش**.
3. **سپس:** Scaffolding (فاز صفر) → توقف → Priority Planning (فاز یک) → توقف → Execution (فاز دو) → QA Gates (فاز سه) → Documentation (فاز چهار) → **Packaging و تحویل ZIP** (فاز پنج).
4. **Resume:** `git status` + `PROJECT_STATE.md` + Memory Bank + `docs/CREDIT_LOG.md` → ادامه از تسک بعدی.
5. **در هر دو حالت:** قواعد آهنین بخش ۲۳ مرجع نهایی هستند.
6. **هیچ‌گاه به هیچ remote‌ای push نکن.**

## ۰.۵. چشم‌انداز پروژه (مرجع اصلی — بدون نیاز به خواندن مخزن GitHub)

پروژه‌ای که ایجنت باید **از صفر بسازد**، یک **پلتفرم داده‌محور و کتابخانه‌ای برای ماژول GSM/GPRS/GPS SIM800** است که شامل اجزای زیر است:

### ۰.۵.۱. اجزای نرم‌افزاری (Python Packages داخل `src/`)

| پکیج | نقش |
|------|-----|
| `sim800_driver` | درایور سطح پایین برای AT Commands ماژول SIM800 (ارسال/دریافت، timeout، retry) |
| `sim800_adapter` | آداپتور برای کتابخانه‌های موجود مانند TinyGSM و سازگاری با APIهای رایج |
| `sim800_tools` | ابزارهای کاربردی (CLI، پیکربندی، تست تعاملی) |
| `sim800_validation` | اعتبارسنجی داده‌های استخراج‌شده در برابر JSON Schema و قواعد دامنه |
| `sim800_diffing` | مقایسه نسخه‌های مختلف دیتاشیت و تشخیص تغییرات در AT Commands |

### ۰.۵.۲. محصولات داده‌ای (Datasets در `dataset/`)

از دل دیتاشیت‌های PDF (در مخزن جداگانه)، ایجنت باید محصولات داده‌ای زیر را تولید کند (حداقل شامل این‌ها؛ ایجنت می‌تواند موارد دیگر را هم بر اساس محتوای PDFها اضافه کند):

| `product_id` | توضیح | خروجی |
|--------------|-------|--------|
| `commands` | فهرست کامل AT Commands با پارامترها و پاسخ‌ها | `dataset/commands.jsonl` |
| `deprecated_commands` | AT Commands حذف‌شده در نسخه‌های جدید | `dataset/deprecated_commands.jsonl` |
| `error_codes` | کدهای خطا (CME/CMS) و توضیح کوتاه | `dataset/error_codes.jsonl` |
| `commands_versions` | ماتریس سازگاری Command × نسخه دیتاشیت | `dataset/commands_versions.jsonl` |

هر محصول باید JSON Schema در `data/schemas/[product_id].schema.json` داشته باشد.

### ۰.۵.۳. دیتاشیت‌ها (PDF)

PDFهای منبع در مخزن جداگانه `https://github.com/AliNazarvand/Package-Datasheet-sim800` نگهداری می‌شوند. ایجنت این مخزن را **فقط به‌صورت read-only** برای خواندن PDFها clone می‌کند. لیست دقیق PDFها از **محتوای همین مخزن** استخراج می‌شود (نه از حافظه، نه از اینترنت).

### ۰.۵.۴. اسناد و مستندات

- `README.md` — معرفی پروژه و نصب
- `ARCHITECTURE.md` — معماری پکیج‌ها و جریان داده
- `docs/` — مستندات تفصیلی (Schemaها، استخراج، مجوز، QA)
- `docs/adr/` — Architecture Decision Records
- `docs/CHANGELOG.md` — طبق Keep a Changelog

### ۰.۵.۵. زیرساخت کیفیت

- `pyproject.toml` با تنظیمات Ruff، mypy، pytest
- `.pre-commit-config.yaml`
- `tests/` — تست‌های واحد و یکپارچگی (پوشش ≥ 80%)
- `.gitignore`, `.gitattributes`
- `data/validation/` — گزارش‌های QA

### ۰.۵.۶. محدودیت‌های حقوقی

- **هیچ محتوای دارای حق نسخه‌برداری SimCom در خروجی نهایی نباشد.** فقط فیلدهای ساختاری (نام AT Command، پارامترها، فرمت پاسخ، کد خطا) منتشر می‌شوند. توضیحات طولانی و جداول کامل PDF منتشر نمی‌شوند.
- مجوز پروژه: ایجنت باید از کاربر بپرسد (پیش‌فرض پیشنهادی: MIT). اگر کاربر پاسخ نداد، در گزارش ذکر و از MIT به‌عنوان پیش‌فرض مستند استفاده شود.

## ۹. روش Clone (فقط مخزن دیتاشیت، فقط خواندن)

### ۹.۱. محدودیت‌ها

- **تنها مخزنی که clone می‌شود: `Package-Datasheet-sim800`.**
- مخزن اصلی (`sim800-platform-all`) **هرگز clone نمی‌شود**.
- **هرگز push نمی‌شود.**
- روش `https://x-access-token:${GH_TOKEN}@github.com/...` استفاده نشود.
- روش `git -c http.extraheader=...` استفاده نشود.

### ۹.۲. روش مجاز

```bash
mkdir -p /workspace/build
cd /workspace/build
# اگر repo عمومی است:
git clone --depth 1 https://github.com/AliNazarvand/Package-Datasheet-sim800.git
# اگر خصوصی است: از کاربر درخواست توکن موقت شود و فقط با credential helper موقت (بخش ۹.۳)
```

**نکته:** چون مخزن دیتاشیت فقط برای خواندن PDFهاست و push ممنوع است، نیازی به نگهداری credential برای push نیست.

### ۹.۳. اگر مخزن دیتاشیت خصوصی است

روش امن — credential helper موقت در `/tmp`:
```bash
export GIT_CREDENTIAL_FILE="/tmp/.git-credentials-$$"
echo "https://x-access-token:${GH_TOKEN}@github.com" > "$GIT_CREDENTIAL_FILE"
chmod 600 "$GIT_CREDENTIAL_FILE"
git config --global credential.helper "store --file=$GIT_CREDENTIAL_FILE"
git clone --depth 1 https://github.com/AliNazarvand/Package-Datasheet-sim800.git
git config --global --unset credential.helper
rm -f "$GIT_CREDENTIAL_FILE"
unset GIT_CREDENTIAL_FILE
```

**پاکسازی الزامی بلافاصله پس از clone.**

### ۹.۴. تنظیمات Git محلی (فقط برای پروژه ساخته‌شده)

پس از ساخت پوشه پروژه در `/workspace/build/sim800-platform-all/`:
```bash
cd /workspace/build/sim800-platform-all
git init -b main
git config user.name "AI Agent"
git config user.email "agent@localhost"
```

**هیچ remote اضافه نکن.**

### ۹.۵. Pre-commit Hooks

پس از ساخت اولیه پروژه:
1. `.pre-commit-config.yaml` بساز.
2. `pre-commit install` را در repo محلی اجرا کن (hook محلی است، نه remote).
3. قاعده اجرا:
   - اگر hook نصب است: از طریق `git commit`.
   - در غیر این صورت: `pre-commit run --all-files` دستی.
4. Exit code:
   ```bash
   pre-commit run --all-files 2>&1 | tee /tmp/precommit.log
   PRECOMMIT_EXIT=${PIPESTATUS[0]}
   ```

## ۱۵. متدولوژی استخراج از PDF (Appendix A)

بدون تغییر نسبت به نسخه قبلی. مراحل زیر حفظ می‌شوند:

### ۱۵.۱. مرحله ۰ — بررسی سلامت PDF

**الف) رمزدار بودن:**
```bash
pdfinfo input.pdf 2>&1 | grep -i "encrypted"
```
اگر رمزدار: در `MISSING_DATASHEETS.md` با برچسب `encrypted` ثبت، از کاربر رمز یا نسخه بدون رمز درخواست شود. **هرگز رمز شکسته نشود.**

**ب) خراب بودن:**
```bash
pdftotext input.pdf - 2>&1 | head -5
```
اگر `Syntax Error` یا `Corrupt`: ثبت با برچسب `corrupted`.

**ج) اندازه و تعداد صفحه:**
```bash
pdfinfo input.pdf | grep -E "^Pages|^Page size|^File size"
```

**د) خالی بودن:** اگر `pdftotext` خروجی خالی/نامفهوم داد → مرحله ۳ (OCR).

**ثبت در `data/validation/pdf_health.json`.**

### ۱۵.۲. مدیریت PDFهای بزرگ

اگر PDF بیش از 500 صفحه یا 50MB: پردازش Chunked با `pdftotext -f/-l` و در صورت نیاز OCR در Chunk.

### ۱۵.۳. مرحله ۱ — تشخیص نوع PDF

`pdftotext -f 1 -l 1 input.pdf -` → متنی یا تصویری.

### ۱۵.۴. مرحله ۲ — استخراج از PDF متنی

- متن ساده: `pdftotext -layout input.pdf output.txt`
- جدول‌ها با `pdfplumber.extract_tables()`
- Fallback: regex روی متن layout

### ۱۵.۵. مرحله ۳ — استخراج از PDF تصویری (OCR)

`pdftoppm -r 300 -png` + `tesseract --psm 6` و `--psm 4` (Double-Pass).

**معیار discrepancy:** نرخ = (تعداد فیلدهای متفاوت) ÷ (کل فیلدها). حداقل 5 رکورد دستی با PDF مقایسه.

### ۱۵.۶. مرحله ۳ب — مسیر نهایی در صورت شکست همه روش‌ها

فیلد → `null` + `extraction_notes` + انتقال رکورد به `data/quarantine/`.

### ۱۵.۷. مرحله ۴ — ادغام AT Commandهای چندصفحه‌ای

ثبت در `data/validation/multipage_commands.md`.

### ۱۵.۸. مرحله ۵ — Footnoteها

فقط در `extraction_notes` ذکر شوند.

### ۱۵.۹. مرحله ۶ — اعتبارسنجی خروجی

در برابر JSON Schema. رکورد نامعتبر → `data/quarantine/`.

## ۱۸. فاز دو — اجرای تدریجی

از بالاترین اولویت شروع و یکی‌یکی پیش برو.

### ۱۸.۱. تعریف Cycle

**یک Cycle = یک تسک در فاز دو.** در پایان هر Cycle، گزارش فاز پنج (متناسب با اندازه تسک) ارائه می‌شود.

### ۱۸.۲. ادامه کار بین Sessionها

**در ابتدای هر Session جدید:**
1. `cd /workspace/build/sim800-platform-all && git status`.
2. `git stash list`.
3. اگر تغییرات uncommitted:
   - مربوط به تسک ناتمام → بررسی، تست، commit (`wip(task-id): ...`).
   - ناشناخته → ثبت در `docs/UNCOMMITTED_CHANGES.md` + سؤال از کاربر.
4. خواندن `PROJECT_STATE.md`، Memory Bank، `docs/CREDIT_LOG.md`.
5. شناسایی آخرین تسک `Done` یا `In Progress`.
6. ادامه از تسک بعدی بر اساس `Rank`.
7. اگر `In Progress` وجود دارد، ابتدا آن تکمیل شود.
8. تناقض Memory Bank و جدول → **جدول اولویت دارد**.

### ۱۸.۳. قبل از اجرا

- ورودی‌ها، خروجی‌ها، شرط پذیرش (DoD) صریح.
- وابستگی‌ها تکمیل و تأیید شده.
- ابهام → سؤال یا فرض مستند.
- **مدیریت Context:** فقط فایل‌های مرتبط. حداکثر 5 فایل در هر مرحله.
- **تقسیم تسک:** اگر > 5 فایل نیاز است یا > 30 دقیقه تخمینی → زیرتسک‌های کوچک‌تر.

### ۱۸.۴. حین اجرا

- کد در ساختار پوشه‌ای موجود.
- **نام‌گذاری `src/`:** underscore + `__init__.py`.
- رعایت استانداردها (Ruff، mypy، typing کامل).
- docstring برای همه توابع و ماژول‌ها.
- کد idempotent و reproducible.
- لاگ دقیق و قابل بازتولید برای اسکریپت‌های استخراج.
- پرهیز از Hard-code مسیر، مقادیر جادویی، secrets.

### ۱۸.۵. مدیریت Secrets

- همه secrets از Env Vars (فقط برای clone مخزن دیتاشیت).
- `.env.example` با placeholder.
- `.env` در `.gitignore`.

### ۱۸.۶. مدیریت Backup

- قبل از هر عملیات داده، backup در `data/backup/`.
- فرمت: `[filename].[timestamp].bak`.
- فقط 5 نسخه آخر:
  ```bash
  ls -1t data/backup/${filename}.*.bak 2>/dev/null | tail -n +6 | xargs -r rm
  ```
- اگر backup شکست خورد: عملیات داده شروع نشود.

### ۱۸.۷. شفافیت داده‌ای

قبل و بعد از هر عملیات داده، لاگ در `logs/data_[task-id]_[timestamp].log`:
- تعداد رکوردهای ورودی/خروجی/ردشده
- دلیل رد هر رکورد
- Transformationها
- Hash SHA-256 ورودی و خروجی

### ۱۸.۸. مدیریت خطا و Rollback

اگر تست Fail یا اسکریپت خطا:
1. لاگ کامل در `logs/error_[task-id]_[timestamp].log`.
2. حداکثر 2 بار تلاش (هر بار رویکرد متفاوت).
3. پس از 2 بار: `Blocked` + تسک بعدی.
4. **هرگز Skip/Disable تست بدون تأیید کاربر.**
5. **حلقه بی‌پایان:** 3 بار متوالی همان عمل با همان رویکرد و ورودی، بدون پیشرفت قابل مشاهده → توقف و گزارش.

### ۱۸.۹. بعد از اجرا — Quality Checks

**ترتیب:**
1. اگر pre-commit به‌عنوان hook نصب است: `git commit` → hook اجرا.
2. اگر نصب نیست: `pre-commit run --all-files` دستی.
3. اگر pre-commit نیست: `ruff check .` و `mypy src/`.
4. رفع خطاها، re-stage، commit.
5. اگر پس از 2 بار همچنان خطا: در گزارش ذکر، بدون pre-commit commit.

**تست‌ها:**
- pytest (حداقل 80٪ پوشش کد جدید).
- اگر 80٪ ممکن نیست: حداقل یک Smoke Test برای هر ماژول + limitation در docstring.

### ۱۸.۱۰. بازنگری Schema موجود

اگر Schema نیاز به تغییر دارد:
1. توقف، داده تولید نشود.
2. ADR پیشنهادی در `docs/adr/ADR-NNN-schema-revision-[product-id].md`.
3. ارائه ADR، دریافت تأیید کاربر.
4. پس از تأیید: Schema به‌روز، re-validate، داده نامعتبر → `data/quarantine/`.
5. **هرگز Schema بدون ADR و تأیید تغییر ندهد.**

### ۱۸.۱۱. Spot-Check دستی

- برای هر PDF، حداقل 5 AT Command استخراج‌شده دستی با PDF مقایسه.
- تطابق 100٪ در `command_text`، `response_format`، `parameters`.
- نتیجه در `data/validation/spotcheck_[pdf-name].md`.

**عدم تطابق:**
1. ثبت در `data/validation/spotcheck_failures.md`.
2. بررسی و اصلاح اسکریپت.
3. تولید مجدد.
4. Spot-Check مجدد.
5. پس از 2 بار Fail: تسک `Blocked`.

### ۱۸.۱۲. Commit (فقط محلی)

```
<type>(<scope>): <description>

انواع: feat, fix, docs, test, chore, refactor, perf, ci, build, wip
```

- **`git commit` فقط. هیچ `git push`، هیچ `git remote add`، هیچ `git remote set-url`.**
- به‌روزرسانی وضعیت تسک در `PROJECT_STATE.md` (✅ / 🔄 / ⏸️).
- به‌روزرسانی Memory Bank.
- افزودن ردیف به `docs/CREDIT_LOG.md`.

- در 90٪ بودجه: هشدار.
- بیش از بودجه: توقف و درخواست تأیید.

## ۲۰. فاز سه — QA Gates

- **Gate 1 — Schema Conformance:** همه رکوردهای JSONL معتبر.
- **Gate 2 — Data Completeness:** هیچ فیلد اجباری خالی نباشد.
- **Gate 3 — Cross-Reference:** ارجاعات یکتا و سازگار.
- **Gate 4 — Reproducibility:** اجرای مجدد = همان خروجی (SHA-256).
- **Gate 5 — CI Green:** وضعیت CI (یا `N/A` اگر CI وجود ندارد).
- **Gate 6 — License Compliance (محتوای PDF):** هیچ محتوای دارای حق نسخه‌برداری در خروجی نباشد.
- **Gate 7 — License Compatibility (dependencyها):** همه dependencyها با مجوز پروژه سازگار.

### ۲۰.۱. Gate 5 — شرط نبود CI

- اگر `.github/workflows/*.yml` وجود دارد: **اجرا نمی‌شود** (چون هیچ remote‌ای وجود ندارد). فقط syntax check می‌شود.
- اگر CI وجود ندارد: Gate 5 = `N/A (No CI configured)`.

### ۲۰.۲. Gate 6 و 7 — تعامل

- **Gate 6** درباره محتوای استخراج‌شده از PDFهای SimCom (خروجی، نه dependency).
- **Gate 7** درباره مجوز dependencyهای نرم‌افزاری (نه محتوای PDF).
- مستقل، هر دو اجرا شوند.

### ۲۰.۳. تعریف «فیلد ساختاری» برای Gate 6

**فیلدهای ساختاری مجاز:**
- نام دستور AT (مثل `AT+CMGF`)
- پارامترها (نام، نوع، محدوده)
- فرمت پاسخ (structure، نه متن کامل نمونه)
- کدهای خطا (شماره و توضیح کوتاه در حد یک جمله)
- سازگاری نسخه (applicable_versions)

**فیلدهای غیرساختاری که منتشر نمی‌شوند:**
- متن توضیحات کامل از دیتاشیت (بیش از 1-2 جمله)
- جداول کامل به‌همان شکل PDF
- نمودارها و تصاویر
- مثال‌های طولانی متن
- مقدمه‌ها، فصل‌بندی‌ها، فهرست‌ها

### ۲۰.۴. معیارهای کمی کیفیت داده

- درصد `null` هر ستون: <= 5٪ (به‌جز فیلدهای اختیاری).
- حداقل رکورد هر محصول: طبق `minimum_records` در Catalog.
- نرخ OCR discrepancy: <= 5٪.
- نرخ رکوردهای رد شده: <= 2٪.

### ۲۰.۵. Gate 4 — Reproducibility

- SHA-256.
- Hash در `data/validation/reproducibility_hash.txt`.
- `.gitattributes` برای تثبیت line endings.
- اگر hash تغییر کرد: دلیل در `extraction_notes`.
- حداقل یک بار بازتولید کامل.

### ۲۰.۶. Gate 6 — License Compliance

- برای هر فایل استخراج‌شده، `LICENSE_EXTRACTION.md`.
- اگر PDF دارای حق نسخه‌برداری: فقط فیلدهای ساختاری (بخش ۲۰.۳).
- اسکریپت `scripts/check_license.py`.

### ۲۰.۷. Gate 7 — License Compatibility

- اسکریپت `scripts/check_license_compatibility.py`.
- نتیجه در `docs/LICENSE_COMPATIBILITY.md`.

**نقطه تأیید #3:** اگر هر Gate Fail شد، توقف، گزارش، منتظر تأیید.

## ۲۳. قواعد آهنین (Hard Rules)

1. **هیچ‌وقت بدون تست کد ننویس.** اگر ممکن نیست، مستند کن.
2. **هیچ‌وقت بدون خواندن دیتاشیت اصلی داده استخراج نکن.**
3. **هیچ‌وقت dependency جدید بدون توجیه اضافه نکن.**
4. **هیچ‌وقت ساختار پوشه را بدون ADR تغییر نده.**
5. **هیچ‌وقت روی هیچ remote‌ای push نکن.** مطلقاً.
6. **هیچ‌وقت PDF اصلی را در پروژه commit نکن.** (در `.gitignore`).
7. **هیچ‌وقت در داده حدس نزن.** فیلد `null` + `extraction_notes`.
8. **قبل از تسک بعدی، خروجی تسک قبلی را اعتبارسنجی کن.**
9. **تفاوت «دانستن» و «فرض کردن» را شفاف بیان کن.**
10. **تسک بزرگ را به زیرتسک بشکن.**
11. **در حلقه بی‌پایان نمان** (3 بار متوالی همان عمل با همان رویکرد و ورودی، بدون پیشرفت قابل مشاهده).
12. **Secrets در کد/config/commit نباشد.**
13. **تست Skip/Disable نکن** مگر با تأیید کاربر.
14. **قبل از عملیات داده backup بگیر** (5 نسخه آخر، در `.gitignore`).
15. **Memory Bank در `PROJECT_STATE.md` به‌روز نگه دار.**
16. **بدون دسترسی تأییدشده به دیتاشیت شروع نکن.**
17. **توکن/credential در لاگ/خروجی/commit چاپ نکن.** هرگز از `https://TOKEN@github.com` استفاده نکن.
18. **قبل از تولید داده، وجود Schema را چک کن.**
19. **محتوای دارای حق نسخه‌برداری SimCom در خروجی نهایی نباشد.** فقط فیلدهای ساختاری.
20. **تفاوت‌های نسخه‌های دیتاشیت را در `data/diffs/` ثبت کن.**
21. **مجوز پروژه را فرض نکن.** اگر `LICENSE` نیست، از کاربر بپرس (پیش‌فرض MIT با تأیید).
22. **هیچ clone از مخزن اصلی انجام نده.** فقط مخزن دیتاشیت.
23. **در ابتدای Session جدید از صفر شروع نکن.** `git status` + `PROJECT_STATE.md` + Memory Bank.
24. **روش مدیریت dependency را آگاهانه انتخاب و مستند کن.**
25. **اعداد و فهرست‌ها را از فایل‌های برنامه‌ریزی ساخته‌شده تأیید کن.**
26. **رمز PDF را نشکن.**
27. **Schema موجود را بدون ADR تغییر نده.**
28. **pre-commit:** اگر hook نصب است، از طریق commit؛ در غیر این صورت دستی.
29. **در پایان هر Session، در صورت نیاز، ZIP موقت از پروژه بساز.** (چون هیچ push‌ای نداریم، back-up محلی حیاتی است.)
30. **ماندگاری محیط را تست کن.**
31. **زبان کد و commitها انگلیسی.** مستندات کاربری می‌توانند فارسی باشند.
32. **این پرامپت را در هر Session دوباره کامل نخوان.**
33. **در pipelineهای Bash از `${PIPESTATUS[0]}` استفاده کن، نه `$?`.**
34. **`docs/CREDIT_LOG.md` را بعد از هر عملیات مهم به‌روز کن.**
35. **پوشه‌های داخلی `src/` باید underscore داشته باشند.** نام dist در `pyproject.toml` می‌تواند خط تیره داشته باشد.
36. **هیچ remote Git اضافه نکن.** `git remote -v` باید خالی باشد.
37. **در فاز پنج (Packaging)، MANIFEST.txt با SHA-256 همه فایل‌ها بساز.**
